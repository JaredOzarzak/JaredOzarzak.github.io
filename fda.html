FDA Device Reports: What Gets Reported, and Can You Trust the Data?

Why this project

Public data is free. Clean data isn't.

The FDA publishes every medical device adverse event report it receives. It's a goldmine for hospitals, device companies, and quality teams, but the raw data comes back as messy, nested JSON with bad dates, inconsistent text, and missing fields. I wanted to do what a data analyst actually does on day one of a job: pull data from a real source, clean it, load it into a database, and prove it's trustworthy before answering anything.

Why keep reading: this isn't just a chart. It's the full pipeline (API → cleaning → quality checks → SQL → findings), with 5 automated checks that run before any number gets trusted.
The data

What and where

  • Source: FDA MAUDE adverse event reports through the public openFDA REST API
  • Scope: reports received in 2025, pulled as 10,000 records through 10 paginated API calls of 1,000 each, with automatic retries
  • Fields kept: 11, flattened out of nested JSON: report ID, date received, date of event, event type, report source, generic name, brand name, manufacturer, product code, device class, medical specialty
  • Caveats: these are the first 10,000 reports the API returned, not a random sample, and a report doesn't prove a device caused harm
The analysis

How I did it, and why each tool

1. Pull: Python + requests

The API caps each call at 1,000 records, so I wrote a loop that pages through 10 calls, retries on errors, and pauses between requests so I don't hit rate limits.

2. Audit before cleaning

Before touching anything, I profiled every field (percent missing, unique values, duplicate report IDs). You can't fix what you haven't measured.

3. Clean: pandas

Removed duplicate reports, converted text dates to real dates (bad values became blank instead of crashing), standardized text (trimmed and uppercased) so "Infusion Pump" and "infusion pump " count as one device, and grouped junk event types like "No answer provided" into UNKNOWN.

I also calculated reporting lag (days from event to FDA receipt) and set a valid range of 0–3,650 days. Any report outside it, either "received" before the event happened or over 10 years later, gets flagged as missing instead of letting them skew the average.

4. Query: SQLite + SQL

I loaded the clean table into SQLite and answered 5 questions with SQL, because that's how analysts query data on the job: event type breakdown, top 10 device types with their injury/death share, monthly volume trend, top manufacturers with average reporting lag, and reports by medical specialty.

-- Monthly reports + % change from the month before
WITH m AS (
  SELECT substr(date_received, 1, 7) AS month, COUNT(*) AS reports
  FROM events GROUP BY month)
SELECT month, reports,
       ROUND(100.0 * (reports - LAG(reports) OVER (ORDER BY month))
             / LAG(reports) OVER (ORDER BY month), 1) AS mom_pct
FROM m ORDER BY month;

Plain English: count reports per month, then compare each month to the one before it. The CTE keeps it readable and the LAG window function does the comparison without a self-join.

5. Visualize

A line chart for the monthly trend (time reads best left to right) and a horizontal bar chart for the top 10 devices (long device names fit on the side).

6. Validate: 5 automated checks

Check built into the pipeline
No duplicate report IDs
Every row loaded into SQL
Event type percentages sum to ~100%
No negative reporting lags
All received dates fall in 2025
What I found

The patterns

  • Public data includes impossible reporting lags, a reminder to validate dates before reporting any time-based metric

What a business could do with this

  • A device company's quality team could track its own products' report volume and injury/death share month over month and act on spikes early
  • Any team reporting "time to report" should filter impossible lags first, or the average will be wrong
Takeaways

The short version

I built a repeatable pipeline from a live government API to a SQL database, caught and handled bad records before they could distort results, and answered real questions with SQL. The pipeline runs 5 automated checks before any number gets reported.
